## 3. 接通飞书，并打通消息链路

飞书接入一开始并没有一次成功，卡在插件依赖上。

最初的核心报错是：

> `Cannot find module 'curve25519-js'`

这意味着不是 AppID / Secret 填错，而是 **Feishu 插件依赖链没有装完整**，所以插件在启动前就挂了。

今天的处理方式是：

1. 给相关依赖链补上 `curve25519-js`
2. 重启 Gateway
3. 再次检查 Feishu 插件日志
4. 完成飞书 pairing
5. 验证机器人能够正常收发消息

最后确认到的关键日志包括：

- `starting feishu[default] (mode: websocket)`
- `bot open_id resolved`
- `WebSocket client started`
- `ws client ready`

这说明飞书链路已经真正起来了，而不是只把配置写上去。

## 7. 排查 Gateway 不稳定问题

今天最折腾的部分，其实是 Gateway。

表面现象看起来像：

- Gateway 老挂
- 控制台偶尔不认
- CLI 有时能用，有时不行
- 后台日志一直刷 warning

但实际拆开看，不是单一问题，而是几层问题叠在一起：

### 控制面不稳定

日志里反复出现：

- `pairing required`
- `not-paired`
- `handshake timeout`
- `gateway closed (1000 / 1008)`

这意味着有时不是 Gateway 主进程真的死了，而是**控制连接阶段就被拒掉了**。

### 启动链不够规整

这台机器上的 Gateway 并不是一个完全干净、完全标准的“稳定托管”状态。

所以它会出现一种很烦的体验：

- 进程明明活着
- 但某些控制入口就是接不上
- 用户体感就会像“它又挂了”

### Ollama 环境残留带来的噪音

今天还定位到一条额外的干扰项：

- 启动环境里被注入了 `OLLAMA_API_KEY=ollama-local`

而本机并没有运行 Ollama，所以 OpenClaw 会不断尝试模型发现，然后刷出：

> `Failed to discover Ollama models: TypeError: fetch failed`

这条 warning 不一定直接把 Gateway 弄死，但会持续制造一种“系统一直有毛病”的观感。

## 这次折腾里最重要的经验

### 先把链路打通，再谈优雅

今天最有效的原则还是那句老话：

> 先让系统稳定，再让它优雅。

如果飞书没接通、仓库没拉下来、自动化没跑起来，那讨论结构漂亮不漂亮、日志优雅不优雅，都太早了。

### 自动化要尽量落进仓库

像新闻更新这种规律性工作，最怕依赖“记得手动去做”。

写进仓库的工作流至少有三个好处：

- 改动有历史
- 规则能复盘
- 换机器也容易接

### Gateway 问题不能只看“进程在不在”

今天这个问题最容易误判的一点就是：

- 进程在，不等于控制面正常
- 控制面异常，也不等于服务完全挂了

以后看 Gateway，最好把这几层分开：

- 进程是否活着
- WebSocket 是否通
- pairing / auth 是否正常
- 上层启动环境是否干净
